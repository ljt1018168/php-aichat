## 1. 业务背景与目标

### 1.1 背景

教务、班主任、咨询师在日常工作中频繁需要查询学员的个人信息、学习数据与择校进度。当前只能通过后台逐层点菜单、填筛选条件完成，操作路径长、学习成本高。

本功能在现有后台中嵌入自然语言对话入口，让用户用一句话拿到结构化结果。

### 1.2 Product Goals

| 目标 | 说明 | 衡量方式 |
|------|------|---------|
| G1 降低查询成本 | 一句话替代多步菜单操作 | 单问题平均完成时间 ≤ 15s |
| G2 意图准确 | 正确理解学员/学习/择校三类查询 | 意图识别准确率 ≥ 90% |
| G3 权限严格 | 数据权限与现有后台**完全一致**，不多给一分 | 越权测试用例 100% 拦截 |
| G4 失败可解释 | 查不到时必须说清是**哪种**查不到 | 三类失败场景响应正确率 100% |
| G5 支持追问 | 多轮上下文连续追问 | 指代消解准确率 ≥ 85% |

### 1.3 非目标（明确排除）

- ❌ 不做数据写入（所有工具只读，禁止 INSERT/UPDATE/DELETE）
- ❌ 不做跨系统写操作（不发短信、不改状态、不推钉钉）
- ❌ 不做通用 BI 图表分析（一期只返回表格 + 文字）
- ❌ 不向学员/家长开放，仅后台管理员可用
- ❌ 不做薪资、财务类数据查询（高敏感，明确排除）

## 2. 权限模型（★ 本 PRD 的地基）

权限设计遵循一条铁律：**AI 对话不得绕过任何现有权限规则，也不得获得比后台菜单更多的权限。**

### 2.1 复用现有权限体系

项目已有两套权限机制，本次全部复用，不新建体系：

| 机制 | 实现 | 作用 |
|------|------|------|
| 功能权限（RBAC） | `admin_admin` → `admin_admin_role` → `admin_role_permission` → `admin_permission` | 控制"能不能用某个功能" |
| 数据权限（分校隔离） | `admin_admin_branch`（`admin_id` ↔ `branch_id`） | 控制"能看到哪些分校的数据" |

现有实现：
- `AdminAdmin::permissions($id)` — 取用户全部权限，**`id == 1` 为超级管理员，直接获得所有 `status=1` 权限**
- `AdminAdmin::branchs($id)` — 取用户可访问分校 ID 数组（对应业务表的 `cid` 字段）

### 2.2 工具级权限映射

每个 AI 工具绑定一个现有 `admin_permission` 权限点，不新增平行权限体系：

| 工具 | 映射权限（示例，需按实际 href 校准） |
|------|-----------------------------------|
| `search_student` | 学员管理 · 列表 |
| `get_student_basic` | 学员管理 · 列表 |
| `get_student_contact` | 学员管理 · 详情（含手机号） |
| `get_course_progress` | 学员课程 · 查看 |
| `get_exam_scores` | 考试成绩 · 查看 |
| `get_attendance` | 出勤记录 · 查看 |
| `get_choose_school_plan` | 择校管理 · 查看 |
| `get_application_progress` | 择校管理 · 查看 |
| `get_admission_result` | 录取结果 · 查看 |
| `get_enter_grades` | 考研成绩 · 查看 |

> 映射关系配置化，存于 `config/aichat.php`，不硬编码。

### 2.3 行级权限（分校隔离）

> ⚠️ **字段口径修正（v1.1）**：本 PRD 初稿写的是 `cid`，实测 `stu_info_basic` 建表语句确认，**学员主表的分校字段是 `branch_id`**，不是 `cid`。
> 全局搜索 `app/` 下代码，`cid` 字段在业务查询中**零引用**；`branch_id` 才是实际隔离依据（见 `AttendanceRateService` 中 `sib.branch_id` 的用法）。
> **实现一律以 `branch_id` 为准。** 若个别从表确实用 `cid`，需逐表校准后登记到 `config/aichat.php` 的字段映射中，不得猜测。

**所有涉及学员的查询，必须自动注入分校过滤条件**，无论用户是否在提问中提及分校：

```sql
WHERE branch_id IN (当前用户可访问分校ID列表)
```

过滤所需的分校 ID 来源（优先级从高到低）：

| 来源 | 说明 |
|------|------|
| `Session::get('admin.branchs')` | 登录时已写入，优先取用，避免每次查库 |
| `AdminAdmin::branchs($adminId)` | Session 缺失时回退查 `admin_admin_branch` |

⚠️ **已知隐患（需在架构阶段解决）**：
`AdminAdmin::branchs()` 直接查 `admin_admin_branch` 表。超级管理员（`id == 1`）若未在该表配置记录，`branchs()` 会返回**空数组**，导致超管反而查不到任何数据。

**处理规则（PRD 约定）**：
- `admin_id == 1` → 视为**全部分校可见**，跳过 `branch_id` 过滤（不再依赖该表是否配置）；
- 其他管理员 → 按 `branchs()` 结果过滤；
- `branchs()` 返回空数组且非超管 → **拒绝查询**，返回无权限提示（而非返回空结果）。

### 3.3 响应规范（★ 核心需求）

**必须严格区分以下四种情况，不可混为一谈：**

| 场景 | 判定条件 | 响应模板 | 错误示范（禁止） |
|------|---------|---------|-----------------|
| **无功能权限** | 角色无该工具权限 | "你没有查看【考试成绩】的权限，如需访问请联系分校管理员。" | ❌ "未找到相关记录" |
| **无数据权限** | 学员 `branch_id` 不在可见分校，或不是该班主任名下学员 | "学员【张三】不属于你负责的分校 / 不在你负责的学员名单内，无法查看。" | ❌ "没有该学员的数据" |
| **对象不存在** | 查询无匹配记录 | "未找到姓名为【张三】的学员，请确认姓名是否准确。" | ❌ "你没有权限" |
| **数据为空** | 对象存在但该域无记录 | "学员【张三】暂无考试成绩记录。" | ❌ "查不到" |

**设计红线**：绝不允许出现「因权限被过滤导致返回空，却被表述为数据不存在」的情况。这是本功能最容易出事、也最难被发现的地方。

**重名不是"查不到"（v1.2 补充）**：命中多位同名学员时返回 `reason=ambiguous` + 候选名单（已过权限、已脱敏），请用户确认或提供学员ID；系统与模型均**不得自行挑一位**继续查询。

### 3.4 多轮上下文

> v1.1：技术路线改为纯自建后，以下机制全部由 PHP 侧自建（无外部依赖）。

| 规则 | 说明 |
|------|------|
| 会话标识 | 自建 `ai_chat_conversation` 表，`conversation_id` 绑定 `admin_id` |
| 用户隔离 | 会话行自带 `admin_id`，查询强制带 `WHERE admin_id = 当前用户`，**会话不可跨用户访问** |
| 实体槽位 | 会话内缓存 `student_id`、`student_name`、`branch_id`、时间范围，供后续轮次引用 |
| 指代消解 | "他的成绩呢？" → 复用上轮 `student_id` |
| 槽位失效 | 用户切换查询对象时刷新槽位；会话超过 24 小时或切换学员后清空 |
| 上下文窗口 | 送入 LLM 的历史保留最近 10 轮（20 条消息），超出部分丢弃最早轮次 |
| 历史持久化 | 消息存 `ai_chat_message`，长期可回溯（不受窗口限制，仅影响送入 LLM 的量） |

## 4. 数据安全

### 4.1 脱敏规则

| 字段 | 默认返回 | 完整查看条件 |
|------|---------|-------------|
| 手机号 | `138****1234` | 超管，或持有"学员详情（含手机号）"权限 |
| 身份证 | **不返回** | 超管查看前 6 后 4，其余角色一律不返回 |
| 姓名 | 完整 | 无需额外权限 |
| 家庭住址 | **不返回** | 一律不返回 |
| 成绩 / 出勤 | 完整 | 受工具级 + 行级权限控制 |

**脱敏在 PHP 侧执行**，不依赖 LLM 自觉——LLM 不得接触未脱敏原文。

### 4.2 审计日志

所有对话请求落表 `ai_chat_log`，字段：

| 字段 | 说明 |
|------|------|
| admin_id | 操作人 |
| conversation_id | 会话 ID |
| question | 用户原始提问 |
| intent | 识别出的意图 |
| tool_called | 调用的工具 |
| sql_or_params | 实际查询参数（**不含敏感结果**） |
| permission_result | 权限判定结果（allow / deny_tool / deny_row） |
| response_summary | 响应摘要（**脱敏后**） |
| latency_ms | 耗时 |
| create_time | 时间 |

> ❗ 日志本身含学员信息，需纳入与业务数据同级的访问控制。

### 4.3 受控 SQL 兜底（P1，二期）

仅当所有工具都不匹配时启用，且**必须**叠加：
- 独立只读数据库账号（不复用 `sms` 账号）
- 表白名单（屏蔽薪资、日志、财务类表）
- 强制注入 `cid IN (用户可访问分校)`
- 强制 `LIMIT 200`
- SQL parser 校验（禁 DDL / DML / 多语句），**不可用正则**
- 执行超时 5s

## 6. 技术方案要点（详见架构文档）

> **v1.1 · 决策已定**：采用「**PHP 纯自建 + LLM Function Calling**」架构，**不引入 Dify 或任何外部编排服务**。

- **LLM** 只负责两件事：① 选工具 ② 抽参数。使用 OpenAI 兼容协议的 Function Calling（工具名 + JSON Schema），不生成 SQL
- **PHP 自建** 承担：Agent 循环、权限守卫、`branch_id` 隔离、字段脱敏、业务查询、会话存储、审计日志
- **核心原则**：LLM 全程不接触数据库凭据、不接触未脱敏原文、不接触越权数据

### 6.1 部署形态决策 —— 结论：纯自建

| 形态 | 运维负担 | 数据出境 | 后台接口暴露面 | 月成本（估） | 判定 |
|------|---------|---------|--------------|-------------|------|
| **Dify Cloud（SaaS）** | 无 | ❌ 是（中美） | ❌ **必须公网可达** | $59–159 + LLM | ❌ 否决 |
| **阿里云 ECS 自部署 Dify** | 中（约 13 容器） | ✅ 否 | ✅ 内网互通 | ¥300–500 + LLM | ❌ 未采纳 |
| **纯自建（不引入 Dify）** | 低 | ✅ 否 | ✅ **无新增** | ¥0 + LLM | ✅ **采纳** |

#### 为什么最终选纯自建

1. **Dify Cloud 两个硬伤**（否决主因）
   - 工具调用方向是 **Dify → 你的 PHP**，即 sms3.0 必须**对公网暴露学员查询接口**。后台当前是内网系统（RDS 内网地址），为一个对话功能开公网接口，安全成本远大于省下的运维。
   - Dify Cloud 隐私政策将**中国和美国**均列为数据处理地，不提供驻留地保证。学员姓名、手机号、成绩属敏感个人信息，出境链路合规风险高。

2. **Dify 自部署的收益在本项目不成立**
   - Dify 的独特价值是**可视化编排**——但本项目是 9 个固定工具，不需要拖拽编排；
   - 它替你做的最实用的两件事（多轮上下文、流式输出），自建成本约 100–200 行代码；
   - 权限部分它帮不上，PHP 侧必做——**这部分才是本项目的核心难点**（见第 2 节）。

3. **纯自建的净收益**
   - 零新增基础设施、零数据出境链路、零公网暴露面；
   - 权限守卫与业务查询在同一进程内完成，**不存在"检索发生在权限之前"的结构性风险**。

#### 成本

| 项 | 说明 |
|----|------|
| LLM API（唯一新增成本） | 20 人 × 10 问/天 ≈ 6,000 问/月，约 2,400 万 tokens/月；DeepSeek 量级约 **¥30–50/月** |
| 基础设施 | **¥0**（无新增服务） |

#### 对开源的态度

纯自建 ≠ 自造轮子。以下开源设计已在架构中**借鉴**（见 `ARCHITECTURE.md`）：
- Vanna 的三路召回思想 → 工具描述 + 示例问法（`ToolRegistry`）
- SQLBot 的术语库 → 业务术语表注入 System Prompt
- WrenAI 的语义层 → 工具参数枚举化、状态值映射为中文

## 7. 验收标准

### 7.1 功能验收

| # | 用例 | 预期 |
|---|------|------|
| A1 | "找一下张伟" | 返回学员列表，含姓名/分校/报名状态 |
| A2 | "张三手机号多少" | 返回脱敏手机号 `138****1234` |
| A3 | "张三的成绩怎么样"（追问） | 复用上轮学员，返回成绩 |
| A4 | 用无考试成绩权限的账号问成绩 | 返回"你没有查看【考试成绩】的权限" |
| A5 | 用 A 分校账号查 B 分校学员 | 返回"学员【X】不属于你负责的分校" |
| A6 | 查询不存在的学员 | 返回"未找到姓名为【X】的学员" |
| A7 | 查存在但无成绩记录的学员 | 返回"学员【X】暂无考试成绩记录" |
| A8 | 超管查询任意分校学员 | 正常返回，不受分校限制 |
| A9 | 问薪资相关问题 | 明确拒绝："暂不支持查询薪资类数据" |
| A10 | 对话中途切换学员 | 槽位正确刷新，不串数据 |

### 7.2 安全验收（★ 必测）

| # | 用例 | 预期 |
|---|------|------|
| S1 | A 分校账号尝试查 B 分校数据 | 拦截，且返回**无权限**而非空结果 |
| S2 | 无权限账号尝试调用任意工具 | 拦截 |
| S3 | 尝试通过提问绕过脱敏（"把手机号完整显示"） | 仍返回脱敏值 |
| S4 | 尝试诱导输出身份证 | 一律不返回 |
| S5 | 检查审计日志 | 所有请求（含被拒）均已记录 |
| S6 | 会话隔离 | 用户 A 无法看到用户 B 的会话历史 |

### 7.3 评测集

上线前建立评测集，**每个意图域 ≥ 20 条真实问法**，覆盖同义表达、口语化、错别字，作为准确率基线与回归测试依据。

## 10. 术语表

| 术语 | 说明 |
|------|------|
| 工具（Tool） | 供 LLM 调用的业务查询能力，一个意图对应一个工具 |
| 槽位（Slot） | 多轮对话中缓存的实体（如 `student_id`），用于指代消解 |
| 指代消解 | 把"他"、"这个学员"等代词解析为具体实体 |
| 行级权限 | 控制用户能看到哪些行（本 PRD 中即 `branch_id` 分校隔离） |
| 工具级权限 | 控制用户能否调用某个工具（映射现有 `admin_permission`） |
| 字段级权限 | 控制用户能否看到完整字段值（如手机号脱敏） |
| branch_id | 学员主表的分校 ID 字段，数据权限隔离依据（注意：**不是** `cid`） |
| Function Calling | LLM 原生能力：模型按 JSON Schema 选择工具并返回参数，不生成 SQL |
